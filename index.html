⭐ Deskripsi

Kursus ini mengajarkan cara membawa aplikasi dari laptop ke server yang bisa diakses publik — tanpa asumsi kamu pernah pegang server sebelumnya.

Peserta mulai dari membeli VPS dan domain, masuk lewat SSH, lalu kerja di terminal: pindah direktori, atur izin file, buat user, jalankan service. Setelah itu memasang Nginx, memahami cara kerja reverse proxy, mengunci situs dengan HTTPS, lalu mengemas aplikasi ke dalam container Docker. Terakhir, proses build dan deploy diotomatiskan dengan GitHub Actions — setiap push ke branch main langsung tayang di server.

Setiap modul berakhir dengan praktik di VPS sungguhan. Tidak ada slide teori tanpa perintah yang dijalankan.

🎯 Tujuan kursus

Kursus ini membentuk peserta yang bisa berdiri sendiri: menyiapkan, menjalankan, dan merawat satu server Linux yang melayani aplikasi web — mulai dari instalasi, Nginx sebagai reverse proxy, kontainerisasi dengan Docker, sampai deploy otomatis lewat CI/CD. Saat aplikasi mati (502, container berhenti, deploy gagal), peserta belajar memeriksa satu per satu sampai ketemu penyebabnya, bukan menebak-nebak.

✅ Hasil kursus

Setelah lulus, peserta bisa menyiapkan VPS dari kosong sampai aplikasinya tayang lewat HTTPS, dan setiap rilis berikutnya otomatis — tanpa perlu SSH ke server lagi.

✅ Pengetahuan objektif

  • Peserta tahu struktur direktori Linux dan fungsi direktori utama (/etc, /var/log, /home, /opt).
  • Peserta paham model izin Unix (owner/group/other, baca/tulis/eksekusi) dan akibatnya di file maupun direktori.
  • Peserta paham cara kerja HTTP request/response, status code, dan peran header di reverse proxy.
  • Peserta paham beda image dan container, serta beda volume dan bind mount.
  • Peserta tahu komponen GitHub Actions: workflow, event, job, step, runner.

✅ Pengetahuan konseptual

  • Peserta bisa menjelaskan beda web server dan application server, dan kenapa Nginx dipasang di depan aplikasi.
  • Peserta bisa menjelaskan kenapa TLS ditangani reverse proxy, bukan aplikasinya.
  • Peserta bisa menjelaskan kenapa data di dalam container hilang saat container dihapus, dan bagaimana volume mencegahnya.
  • Peserta bisa menjelaskan beda continuous integration, continuous delivery, dan continuous deployment.
  • Peserta bisa menjelaskan kelebihan dan kekurangan container dibanding mesin virtual, termasuk kapan container bukan pilihan yang tepat.

✅ Pengetahuan prosedural

  • Peserta bisa menyiapkan lingkungan dari nol: instance Ubuntu 24.04, swap, domain dengan record A yang terverifikasi, dan paham firewall-nya ada dua lapis (milik penyedia dan ufw).
  • Peserta bisa mengamankan SSH: login pakai key, matikan login root, tutup port yang tidak dipakai.
  • Peserta bisa memasang Nginx, menulis server block, menguji konfigurasi dengan sudo nginx -t, dan reload tanpa downtime.
  • Peserta bisa memasang reverse proxy lengkap dengan proxy_set_header, dukungan WebSocket, dan HTTPS Let's Encrypt.
  • Peserta bisa menulis Dockerfile multi-stage, membangun image, dan menjalankan aplikasi beserta database pakai Docker Compose.
  • Peserta bisa menulis workflow GitHub Actions yang menjalankan test, membangun image, mendorongnya ke GHCR, lalu deploy ke VPS.
  • Peserta bisa mundur ke versi image sebelumnya kalau deploy bermasalah.

✅ Pengetahuan meta-kognitif

  • Peserta bisa memecah masalah "situs tidak bisa diakses" menjadi lapisan pemeriksaan: DNS, firewall, port, proses, Nginx, aplikasi, log.
  • Peserta bisa membaca log (journalctl, docker logs, /var/log/nginx/error.log) dan mengambil informasi yang relevan sebelum mengubah konfigurasi.
  • Peserta bisa menilai kesiapan rilis dengan checklist go-live, dan tahu tindakan mana yang berbahaya (rm -rf, docker system prune, ufw enable saat masih terhubung SSH).
  • Peserta terbiasa mendokumentasikan perubahan konfigurasi dan mengembalikannya bila gagal.

Ringkasan modul

Inilah titik nol kursus: belum ada server dan belum ada domain. Dua pelajaran di modul ini menghasilkan satu hal sederhana tapi wajib — sebuah server yang bisa kamu SSH dan sebuah nama domain yang mengarah ke server itu.

Semua modul berikutnya bergantung pada dua hal ini. Kalau ssh belum bisa masuk, atau dig belum mengembalikan IP servermu, jangan lanjut dulu.

Hasil pembelajaran

  • Membuat instance VPS Ubuntu 24.04 LTS dan mencatat IP, user awal, serta port SSH.
  • Login pertama lewat SSH, memverifikasi CPU/RAM/disk, dan menambah swap pada server ber-RAM kecil.
  • Mengenali console/VNC penyedia sebagai jalur darurat saat SSH terkunci.
  • Membeli domain dan mengarahkannya ke IP server lewat record A.
  • Membuktikan DNS sudah menyebar dengan dig, dan tahu kenapa itu syarat sebelum meminta sertifikat HTTPS.

Pelajaran 0.1 — Membuat VPS dari nol

Tujuan

Punya satu server Linux yang bisa di-SSH, dari kondisi belum punya apa-apa: memilih penyedia, membuat instance, login pertama, dan memastikan sumber dayanya cukup.

Konsep

VPS (Virtual Private Server) adalah komputer sewaan di pusat data: kamu dapat akses root, IP publik, dan tanggung jawab penuh atas isinya. Berbeda dari shared hosting yang membatasi, di VPS kamu yang mengatur semuanya — termasuk kalau salah konfigurasi sampai server tidak bisa diakses.

Yang perlu diputuskan sebelum membuat instance:

PilihanRekomendasi untuk kursus ini
PenyediaYang punya region Jakarta/Singapore: IDCloudHost, Biznet Gio, DigitalOcean, Vultr, Hetzner, AWS Lightsail
Sistem operasiUbuntu 24.04 LTS (LTS = didukung 5 tahun)
SpesifikasiMinimum 1 vCPU / 1 GB RAM / 25 GB SSD; disarankan 2 vCPU / 2 GB
AlamatIPv4 publik (wajib); IPv6 hanya bonus
AutentikasiSSH key bila bisa; password hanya untuk login pertama
BackupSnapshot otomatis bila tersedia dan murah

Tiga hal yang harus kamu catat setelah instance dibuat: IP publik, user awal (root, ubuntu, atau admin — tergantung penyedia, biasanya dikirim lewat email), dan port SSH (default 22).

Catatan biaya: instance yang dimatikan (shutdown) umumnya tetap ditagih, karena disk dan IP-nya masih dipesan. Yang menghentikan tagihan adalah menghapus instance (destroy). Snapshot sebelum eksperimen berbahaya jauh lebih murah daripada kehilangan server.

Praktik

  1. Buat akun dan instance di panel penyedia.
  • Pilih region terdekat (Jakarta/Singapore) — latensi ke pengguna Indonesia jauh lebih baik.
  • Pilih image Ubuntu 24.04 LTS x86_64, bukan versi minimal/container.
  • Ukuran: mulai dari paket terkecil yang masuk akal; 1 GB RAM cukup untuk Nginx + satu container kecil, 2 GB lebih lega.
  • Kalau panel meminta SSH key: tempel public key dari laptop (cara membuatnya ada di pelajaran 1.4). Kalau hanya password, lanjut dengan password yang dikirim ke email.
  • Beri nama host yang jelas, misalnya devops-web-01.
  1. Catat dan amankan data akses.
IP publik   : 203.0.113.10
User awal   : root (atau: ubuntu)
Port SSH    : 22
Kata sandi  : (dari email penyedia)
Panel/console: https://panel.penyedia.example

Simpan kata sandi awal di pengelola kata sandi, bukan di catatan biasa.

  1. Buka terminal di laptop dan tes jangkauan server.
# macOS/Linux (Terminal) atau Windows 10+ (PowerShell). Cek dulu klien SSH ada:
ssh -V

# Tes port terbuka sebelum login (Linux/macOS):
nc -zv 203.0.113.10 22

# Login pertama:
ssh root@203.0.113.10
# atau, kalau user awalnya ubuntu:
ssh ubuntu@203.0.113.10

Di Windows tanpa klien SSH, pakai PuTTY atau aktifkan OpenSSH Client lewat Settings → Apps → Optional features.

  1. Kenali mesinnya dan pastikan sumber daya sesuai iklan paket.
cat /etc/os-release | head -2      # harus Ubuntu 24.04.x LTS
nproc                              # jumlah CPU
free -h                            # RAM dan swap
df -h /                            # ruang disk
curl -s https://ifconfig.me; echo  # IP publik dari sudut pandang internet
  1. Tambah swap bila RAM hanya 1 GB.

Server kecil tanpa swap bisa membunuh proses sendiri (OOM killer) saat build image Docker. Swap file 2 GB membuat build lebih aman.

sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

# supaya aktif lagi setelah reboot
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

free -h                            # kolom Swap harus terisi
swapon --show
  1. Amankan akses awal — lanjut ke pelajaran 1.4 untuk detailnya.
passwd                                   # wajib bila login memakai password
sudo apt update && sudo apt upgrade -y

Kalau penyedia menyediakan SSH key saat membuat instance, jangan menonaktifkan autentikasi password sebelum key-mu terbukti bisa login.

  1. Pelajari panel penyedia — ini jalur penyelamatanmu.
  • Console / VNC: masuk ke server lewat browser walau SSH sudah terkunci. Ini satu-satunya cara pulih kalau aturan firewall salah.
  • Firewall penyedia / security group: beberapa penyedia punya firewall sendiri di depan server. Kalau port 80 tidak bisa diakses, periksa dua tempat: ufw di dalam server dan firewall di panel.
  • Snapshot/backup: lakukan sebelum perubahan besar.
  • Reboot/hard reboot: reboot dari SSH dulu; hard reboot hanya kalau server benar-benar menggantung.
  • Resize: menaikkan RAM/CPU biasanya butuh reboot; menurunkan biasanya butuh rebuild.
  1. Siapkan kebiasaan kerja.
  • Jangan bekerja sebagai root sehari-hari; buat user deploy (pelajaran 1.4).
  • Jangan pakai IP sebagai satu-satunya catatan; siapkan domain (dipakai mulai modul 2).
  • Kalau instance ini hanya untuk latihan, matikan/hapus setelah selesai supaya tagihan tidak jalan terus.

Pelajaran 0.2 — Domain dan DNS

Tujuan

Membeli satu domain, mengarahkannya ke IP server, dan membuktikan DNS-nya sudah menyebar sebelum dipakai HTTPS.

Konsep

Domain adalah nama sewaan tahunan (mis. example.com). DNS adalah buku telepon yang menerjemahkan nama itu jadi alamat IP. Kamu tidak "memasang" domain di server — kamu menambahkan catatan (record) di DNS yang menunjuk ke IP server.

Record yang dipakai kursus ini:

RecordFungsiContoh
ANama → IPv4app.example.com → 203.0.113.10
AAAANama → IPv6opsional
CNAMENama → nama lainwww → example.com
NSServer nama yang berwenangdari penyedia DNS
TXTVerifikasi & email (SPF/DKIM)tidak dipakai di sini

Istilah penting:

  • Registrar — tempat membeli domain (Namecheap, Cloudflare Registrar, Rumahweb, Niagahoster, Porkbun).
  • Nameserver (NS) — server yang menyimpan record-mu. Bisa di registrar, bisa dipindah ke penyedia DNS lain (Cloudflare, Route 53).
  • TTL — berapa lama record di-cache. TTL 300 detik mempercepat perubahan saat menyiapkan; TTL 3600 lebih hemat query.
  • Subdomain — app.example.com untuk aplikasi, example.com untuk halaman utama.

Kalau kamu memakai proxy CDN di depan domain (mis. awan oranye Cloudflare), validasi HTTP-01 Let's Encrypt bisa gagal karena challenge dijawab oleh proxy. Untuk kursus ini, matikan proxy (awan abu-abu / DNS only) sampai sertifikat terbit.

Menunggu DNS menyebar tidak bisa dipercepat dengan me-restart server. Yang bisa dilakukan: menurunkan TTL sebelum perubahan, dan memverifikasi lewat beberapa resolver.

Praktik

  1. Beli domain.
  • Pilih nama pendek yang mudah diingat; TLD .com/.id/.dev semuanya bisa.
  • Aktifkan auto-renew dan proteksi privasi (WHOIS privacy) bila tersedia.
  • Jangan beli hosting dari registrar kalau kamu sudah punya VPS — cukup domainnya.
  1. Tentukan di mana DNS dikelola.
  • Kalau memakai NS registrar, langsung edit record di panel registrar.
  • Kalau memindahkan NS ke Cloudflare: tambahkan domain di Cloudflare, salin dua NS yang diberikan, tempel di panel registrar, lalu tunggu sampai status domain "Active" di Cloudflare.
  1. Tambahkan record A.
Type : A
Name : app            (atau @ untuk example.com)
Value: 203.0.113.10   (IP VPS-mu)
TTL  : 300
Proxy: DNS only (awan abu-abu) bila memakai Cloudflare

Tambahkan juga www (CNAME ke example.com) dan @ (A ke IP yang sama) bila ingin halaman utama ikut jalan.

  1. Verifikasi dari laptop.
dig +short app.example.com          # harus IP server
dig NS example.com +short           # nameserver yang aktif
dig @1.1.1.1 +short app.example.com # tanya resolver publik
dig @8.8.8.8 +short app.example.com
nslookup app.example.com            # alternatif di Windows

Kalau dig kosong, belum ada jawaban. Kalau mengembalikan IP lama, cache TTL masih berlaku.

  1. Cek dari sisi server juga.
getent hosts app.example.com
curl -sI http://app.example.com | head -3    # 502/404 masih normal: Nginx belum diatur

Koneksi berhasil (walau balasannya error HTTP) berarti DNS + jaringan sudah benar. Could not resolve host berarti DNS belum siap.

  1. Catat semuanya.
Domain      : example.com
Subdomain   : app.example.com
Registrar   : (nama)
DNS dikelola: (registrar / Cloudflare)
Record A    : app -> 203.0.113.10
Tanggal beli: 2026-11-11
Perpanjangan: 2027-11-11

Kriteria selesai: dig +short app.example.com konsisten mengembalikan IP server dari dua resolver berbeda.

Cek pemahaman

  1. Apa beda registrar dan penyedia DNS? — Registrar tempat membeli/memperpanjang domain; penyedia DNS tempat record disimpan (bisa sama, bisa dipindah lewat NS).
  2. Kenapa TTL diturunkan sebelum perubahan besar? — Perubahan tersebar lebih cepat karena cache lama berumur pendek.
  3. Kenapa proxy CDN sebaiknya dimatikan saat menerbitkan sertifikat? — Validasi HTTP-01 dijawab proxy, bukan server, sehingga Let's Encrypt tidak menemukan challenge.
  4. Bagaimana membedakan masalah DNS dan masalah Nginx? — Could not resolve host = DNS; balasan HTTP (502/404) berarti DNS sudah benar dan masalahnya di server.

Pelajaran 1.1 — Terminal dan shell

Tujuan

Membaca prompt, memakai man, dan mengatur environment variable tanpa panic.

Konsep

Terminal adalah jendela. Shell adalah program di dalamnya yang membaca perintahmu — di Ubuntu defaultnya bash.

Prompt khas server:

deploy@web-01:~$
  • deploy — user yang sedang login.
  • web-01 — nama host.
  • ~ — direktori kerja sekarang (~ = home user).
  • $ — kamu user biasa. Kalau #, kamu root. Perhatikan tanda ini sebelum menekan Enter.

Perintah selalu berbentuk nama-perintah [opsi] [argumen]. Shell memecahnya berdasarkan spasi, jadi path dengan spasi harus dikutip: cd "folder saya".

PATH adalah daftar direktori tempat shell mencari perintah. echo $PATH menampilkannya. Kalau muncul command not found padahal paketnya terpasang, biasanya letak binary tidak ada di PATH.

Environment variable adalah pasangan nama=nilai yang diwariskan ke proses anak. Variabel yang di-export terlihat oleh program yang kamu jalankan; variabel tanpa export hanya ada di shell saat itu.

Praktik

  1. Kenali diri sendiri dan mesinnya.
whoami            # user aktif
hostname          # nama server
pwd               # direktori sekarang
echo $SHELL       # shell yang dipakai
cat /etc/os-release | head -3   # versi Ubuntu
  1. Baca dokumentasi tanpa internet.
man ls            # keluar dengan q
ls --help | head -20
man -k permission # cari halaman manual berdasarkan kata kunci
  1. Latihan riwayat dan pelengkapan.
history | tail -10
!!                # jalankan ulang perintah terakhir
sudo !!           # jalankan ulang perintah terakhir sebagai root

Tekan Tab setelah mengetik sebagian nama file atau perintah — shell melengkapinya.

  1. Variabel environment.
export APP_ENV=production
echo $APP_ENV
env | grep APP_          # variabel yang diwariskan ke proses anak
bash -c 'echo $APP_ENV'  # proses anak mewarisi nilainya
unset APP_ENV
  1. Variabel sementara untuk satu perintah saja.
APP_ENV=staging bash -c 'echo $APP_ENV'   # hanya berlaku untuk perintah itu
  1. Simpan permanen di ~/.bashrc (hanya untuk user ini, hanya shell interaktif).
echo 'export EDITOR=nano' >> ~/.bashrc
source ~/.bashrc

GejalaPenyebabSolusi
command not foundPaket belum terpasang, atau binary tidak ada di PATHcommand -v nama untuk cek; kalau kosong, pasang paketnya

Latihan

  2. Buat variabel PROJECT=devops-pro, buktikan proses anak mewarisinya, lalu hapus variabelnya.

Pelajaran 1.2 — Filesystem dan navigasi

Tujuan

Berpindah direktori dan menemukan file dengan cepat, memahami di mana konfigurasi dan log disimpan.

Konsep

Linux punya satu pohon direktori, dimulai dari /. Tidak ada drive C:.

PathIsi

/var/wwwKonvensi letak situs web

/optAplikasi pihak ketiga
/tmpSementara, bisa hilang saat reboot
/usr/binBinary yang dipasang paket

Path absolut mulai dari /. Path relatif dihitung dari direktori sekarang. . adalah direktori ini, .. direktori induk.

Symlink adalah pintu ke path lain. Di Nginx nanti, sites-enabled berisi symlink ke sites-available.

Praktik

  1. Navigasi dasar.
cd /var/log && pwd
cd ..              # naik satu level

mv ~/apps/demo/src/app.py.bak ~/apps/demo/src/app.bak
rm ~/apps/demo/src/app.bak
tree ~/apps          # kalau belum ada: sudo apt install tree

ln -s ~/apps/demo/config ~/demo-config
ls -l ~/demo-config   # panah -> menunjukkan target
readlink ~/demo-config
rm ~/demo-config      # hapus symlink, bukan targetnya
  1. Cari file.
find /etc -name '*.conf' -type f | head
find ~/apps -type f -size +1M
find /var/log -name '*.log' -mtime -1     # diubah dalam 24 jam terakhir
  1. Cari isi file.
grep -rn "server_name" /etc/nginx 2>/dev/null | head
sudo grep -c "ERROR" /var/log/syslog   # /var/log/syslog hanya terbaca root/adm
  1. Cek ukuran pemakai disk — kebiasaan yang menyelamatkan server.
df -h /            # sisa ruang disk
du -sh /var/log/* 2>/dev/null | sort -h | tail -5

Pelajaran 1.3 — File dan teks

Tujuan

Membaca, menyaring, dan memindahkan teks dengan redirect, pipe, dan alat baris perintah.

Konsep

Setiap proses punya tiga saluran: stdin (0), stdout (1), stderr (2). Redirect mengubah tujuannya:

SintaksArti
>stdout ke file, menimpa
>>stdout ke file, menambah di akhir
2>stderr ke file
2>&1stderr ikut ke stdout
`\`stdout proses kiri jadi stdin proses kanan

Ini bukan detail kosmetik. Saat men-debug deploy nanti, docker compose up -d 2>&1 | tee deploy.log menyimpan bukti yang bisa dibaca ulang.

Praktik

  1. Baca file tanpa membuka editor.
cat /etc/hostname
less /etc/services        # navigasi panah, keluar dengan q
head -5 /etc/passwd
sudo tail -f /var/log/syslog    # ikuti baris baru, keluar dengan Ctrl+C
  1. Redirect dan pipe.
echo "baris pertama" > ~/catatan.txt
echo "baris kedua" >> ~/catatan.txt
cat ~/catatan.txt | wc -l
ls /tidak-ada 2> ~/error.txt; cat ~/error.txt
  1. Saring dan olah.
cut -d: -f1 /etc/passwd | sort | uniq | head
grep -v '^#' /etc/ssh/sshd_config | grep -v '^$'
awk -F: '$3 >= 1000 {print $1}' /etc/passwd   # user non-sistem
  1. Ganti teks dengan sed.
sed 's/localhost/127.0.0.1/' file.txt          # tampilkan saja
sed -i.bak 's/localhost/127.0.0.1/' file.txt   # ubah, simpan cadangan .bak
  1. Arsip dan pindahkan.
tar -czf ~/backup-etc-ssh.tar.gz /etc/ssh 2>/dev/null
tar -tzf ~/backup-etc-ssh.tar.gz | head
tar -xzf ~/backup-etc-ssh.tar.gz -C /tmp
  1. Uji HTTP dengan curl — alat yang akan sering dipakai di modul 2.
curl -I https://example.com          # header saja
curl -s -o /dev/null -w '%{http_code}\n' https://example.com
curl -s https://api.github.com | head -20

Pelajaran 1.4 — User, grup, permission, dan SSH

Tujuan

Membuat user deploy, mengatur izin file, dan mengunci akses SSH ke key saja.

Konsep

Setiap file punya owner, group, dan tiga set izin: owner, group, other. rwx untuk file berarti baca, tulis, eksekusi. Untuk direktori, x berarti "boleh masuk", r berarti "boleh daftar isi", w berarti "boleh membuat/menghapus entri".

Angka oktal: r=4, w=2, x=1. 750 = owner rwx, group r-x, other ---.

umask menentukan izin default file baru. umask 022 menghasilkan file 644 dan direktori 755.

Prinsip yang dipakai sepanjang kursus: aplikasi tidak berjalan sebagai root, dan SSH tidak menerima password.

Praktik

  1. Buat user deploy.
sudo adduser deploy
sudo usermod -aG sudo deploy     # hanya jika perlu sudo penuh
id deploy

Untuk server produksi, alternatif lebih ketat: user tanpa sudo, hanya untuk menjalankan aplikasi.

  1. Permission.
mkdir -p ~/apps/demo && cd ~/apps/demo
echo "PORT=3000" > .env
chmod 600 .env            # hanya owner bisa baca/tulis
ls -l .env
mkdir -p public data          # buat dulu; chmod pada direktori yang belum ada akan gagal
chmod 755 public
chmod -R 750 data

Perintah berbahaya: chmod -R 777 membuka semua file untuk semua user. Jangan dipakai sebagai solusi "permission denied" — perbaiki kepemilikan:

sudo chown -R deploy:deploy ~/apps/demo
  1. Buat SSH key di laptop (bukan di server).
ssh-keygen -t ed25519 -C "deploy@laptop"
cat ~/.ssh/id_ed25519.pub
  1. Pasang public key di server.
mkdir -p ~/.ssh && chmod 700 ~/.ssh

Tujuan

Pelajaran 2.2 — Instalasi dan struktur konfigurasi Nginx

Tujuan

Memahami di mana konfigurasi berada dan siklus perubahan yang aman.

Konsep

/etc/nginx/
├── nginx.conf              # konfigurasi utama, berisi http { ... }
├── conf.d/*.conf           # potongan konfigurasi tambahan
├── sites-available/*       # definisi server block (tidak dibaca langsung)
├── sites-enabled/*         # symlink ke sites-available yang aktif
├── snippets/               # potongan yang bisa di-include
└── mime.types

Nginx membaca sites-enabled/ karena ada baris include /etc/nginx/sites-enabled/; di dalam blok http pada nginx.conf. Menonaktifkan situs = hapus symlink-nya, bukan hapus file.

Aturan kerja: setiap perubahan → sudo nginx -t → kalau OK → sudo systemctl reload nginx. Reload menerapkan konfigurasi baru tanpa memutus koneksi yang sedang jalan; restart memutus koneksi.

Praktik

  1. Pasang dan periksa.
sudo apt update
sudo apt install -y nginx
nginx -v
systemctl status nginx --no-pager
ls -l /etc/nginx/
  1. Halaman default.
curl -I http://127.0.0.1
ls -l /var/www/html
  1. Baca konfigurasi utama.
grep -vE '^\s*(#|$)' /etc/nginx/nginx.conf | head -40
  1. Siklus perubahan yang benar.
sudo cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.bak
sudo nano /etc/nginx/sites-available/demo
sudo ln -s /etc/nginx/sites-available/demo /etc/nginx/sites-enabled/demo
sudo nginx -t
sudo systemctl reload nginx
  1. Log.
sudo tail -f /var/log/nginx/access.log
sudo tail -f /var/log/nginx/error.log
  1. Nonaktifkan situs default supaya tidak menabrak server_name.
sudo rm /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

  1. Buat file sites-available/demo minimal, aktifkan dengan symlink, reload, dan akses lewat curl -H 'Host: demo.local' http://127.0.0.1.

  2. Beda reload dan restart? — Reload tanpa memutus koneksi; restart menghentikan lalu menyalakan proses.
  3. Urutan yang benar setelah edit konfigurasi? — nginx -t, lalu reload.

Tugas untuk pertemuan berikutnya

Pelajaran 2.3 — Situs statis pertama

Tujuan

Menyajikan file statis dengan root, index, dan try_files.

Konsep

root /var/www/site; berarti Nginx mencari /var/www/site + path URI. Request /logo.png → /var/www/site/logo.png.

index index.html; menentukan file yang dikirim saat URI berakhir dengan /.

try_files $uri $uri/ =404; adalah pola standar: coba file, coba direktori, kalau tidak ada balas 404 eksplisit. Untuk aplikasi single-page, versi SPA-nya: try_files $uri /index.html;.

Nginx berjalan sebagai user www-data. File yang tidak bisa dibaca www-data menghasilkan 403.

Praktik

  1. Siapkan direktori dan file.
sudo mkdir -p /var/www/demo
sudo chown -R deploy:deploy /var/www/demo
cat > /var/www/demo/index.html <<'HTML'
<!doctype html>
<meta charset="utf-8">
<title>Demo</title>
<h1>Server ini hidup</h1>
HTML
  1. Server block.
sudo nano /etc/nginx/sites-available/demo
server {
    listen 80;
    listen [::]:80;
    server_name demo.example.com;

    root /var/www/demo;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
  1. Aktifkan dan uji.
sudo ln -sf /etc/nginx/sites-available/demo /etc/nginx/sites-enabled/demo
sudo nginx -t && sudo systemctl reload nginx
curl -I -H 'Host: demo.example.com' http://127.0.0.1
curl -s -H 'Host: demo.example.com' http://127.0.0.1 | head -3
  1. Verifikasi kepemilikan dan izin.
namei -l /var/www/demo/index.html
sudo -u www-data cat /var/www/demo/index.html >/dev/null && echo "www-data bisa baca"

  2. Kenapa 403 sering soal izin direktori, bukan file? — Nginx butuh izin x pada setiap direktori di sepanjang path.
  3. Kapan try_files $uri /index.html dipakai? — Untuk aplikasi single-page yang menangani routing di sisi klien.

Tugas untuk pertemuan berikutnya

Kerjakan: Sajikan satu situs statis dengan CSS sendiri dan halaman 404 kustom.

Siapkan: Siapkan daftar 3 subdomain yang ingin kamu buat (aplikasi, staging, admin).

Bawa bukti: curl -I untuk 200 dan 404 + output namei -l pada file yang disajikan.

Pelajaran 2.4 — Server block dan domain

Tujuan

Melayani beberapa domain di satu server dan mengarahkan HTTP ke HTTPS.

Konsep

server_name mencocokkan header Host. Nginx memilih server block paling cocok; kalau tidak ada yang cocok, dipakai block dengan default_server.

Pola redirect yang benar: satu block listen 80 untuk redirect, satu block listen 443 ssl untuk melayani.

Praktik

  1. Beberapa domain, satu server.
server {
    listen 80;
    server_name example.com www.example.com;
    root /var/www/company;
    index index.html;
}

server {
    listen 80;
    server_name app.example.com;
    root /var/www/app-public;
    index index.html;
}
  1. Tangkap semua nama yang tidak dikenal.
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    server_name _;
    return 444;    # tutup koneksi tanpa balasan
}
  1. Redirect HTTP ke HTTPS sekaligus menormalkan www.
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;
    return 301 https://example.com$request_uri;
}

Jangan membuat blok listen 80 kedua dengan server_name www.example.com; Nginx akan mencatat conflicting server name dan salah satu blok diabaikan.

  1. Kalau www tetap ingin dipertahankan tetapi selalu dialihkan ke non-www di HTTPS, tambahkan satu blok 443 khusus:
server {
    listen 443 ssl http2;
    server_name www.example.com;
    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    return 301 https://example.com$request_uri;
}

Sertifikat harus mencakup www.example.com (-d www.example.com saat menerbitkan), kalau tidak browser memperingatkan nama tidak cocok.

  1. Uji pemilihan block.
curl -sI -H 'Host: app.example.com' http://127.0.0.1 | head -1
curl -sI -H 'Host: tidak-dikenal.local' http://127.0.0.1 | head -1

Kalau error

GejalaPenyebabSolusi
conflicting server name di error logserver_name sama di dua blockHapus/ubah salah satu
Loop redirectHTTPS block juga me-redirect ke HTTPSPastikan redirect hanya di block port 80
Domain lain ikut melayaniSemua masuk default_serverTambahkan block server_name yang tepat

Latihan

  1. Buat dua domain berbeda dilayani satu Nginx, buktikan dengan curl memakai header Host.
  2. Tambahkan redirect permanen dari www ke non-www, dan buktikan kode 301.

Kriteria selesai: request ke nama yang tidak terdaftar tidak membocorkan situs mana pun.

Cek pemahaman

  1. Apa fungsi default_server? — Block yang dipakai saat tidak ada server_name yang cocok.
  2. Kenapa return 301 lebih baik daripada rewrite untuk redirect domain? — Lebih sederhana, lebih cepat, dan tidak melibatkan evaluasi regex.
  3. Di block mana redirect HTTP→HTTPS harus diletakkan? — Di block listen 80, bukan di block SSL.

Tugas untuk pertemuan berikutnya

Kerjakan: Buat dua server block berbeda + satu default_server yang membalas 444 + redirect www ke non-www.

Siapkan: Sebelum menguji, tulis tebakanmu: blok mana yang menangani tiap nama?

Bawa bukti: Tiga output curl -sI -H 'Host: ...' dan bandingkan dengan tebakanmu.

Pelajaran 2.5 — location dan routing

Tujuan

Mengarahkan URI ke tujuan yang tepat, dan tahu urutan pencocokan Nginx.

Konsep

Urutan pencocokan location:

  1. location = /path — cocok persis, prioritas tertinggi.
  2. location ^~ /path — prefix yang menghentikan pencarian regex.
  3. location ~ pola / ~* pola — regex (case-sensitive / tidak), urut kemunculan.
  4. location /path — prefix terpanjang menang.

root menempelkan path ke URI; alias menggantinya. Kesalahan klasik: memakai alias dengan URI yang berakhir / tanpa menutup alias dengan /.

Praktik

  1. Demonstrasi urutan.
server {
    listen 80;
    server_name route.example.com;
    root /var/www/route;

    location = /health { return 200 "ok\n"; }
    location ^~ /static/ { }
    location ~* \.(jpg|png|css|js)$ { expires 7d; }
    location / { try_files $uri $uri/ =404; }
}
sudo nginx -t && sudo systemctl reload nginx
curl -s -H 'Host: route.example.com' http://127.0.0.1/health
  1. root vs alias.
location /files/ { root /srv/data; }    # /files/a.txt -> /srv/data/files/a.txt
location /media/ { alias /srv/photos/; } # /media/a.jpg -> /srv/photos/a.jpg
  1. return dan rewrite.
location = /lama { return 301 /baru; }
rewrite ^/artikel/(\d+)$ /post/$1 permanent;
  1. Halaman error sendiri.
sudo mkdir -p /var/www/demo/errors && echo "<h1>404</h1>" | sudo tee /var/www/demo/errors/404.html
error_page 404 /errors/404.html;
location = /errors/404.html { internal; }
  1. Uji semuanya dengan curl.
for p in /health /static/x.css /a.jpg /lama /tidak-ada; do
  printf '%s -> ' "$p"; curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: route.example.com' "http://127.0.0.1$p"
done

Latihan

  1. Buat location = /health yang membalas 200 tanpa menyentuh disk.
  2. Buat location /media/ memakai alias ke direktori luar root dan buktikan file termuat.

Kriteria selesai: kamu bisa menebak lokasi mana yang menangani sebuah URI, lalu membuktikannya dengan curl.

Cek pemahaman

  1. Mana yang menang: = /a atau ~ \.php$ untuk URI /a? — = /a, karena pencocokan persis paling tinggi.
  2. Beda root dan alias? — root menambahkan URI ke path; alias menggantikan bagian yang cocok.
  3. Fungsi internal;? — Melarang akses langsung dari klien; hanya boleh dipakai lewat error_page/redirect internal.

Kerjakan: Buat 5 location dengan jenis pencocokan berbeda (persis, ^~, regex, prefix, alias), lalu uji URI yang sama ke semuanya.

Pelajaran 2.6 — Reverse proxy

Tujuan

Meneruskan request ke aplikasi di 127.0.0.1:3000 dengan header yang benar, termasuk WebSocket.

Konsep

Reverse proxy berdiri di depan aplikasi: klien bicara ke Nginx, Nginx bicara ke aplikasi. Keuntungan: TLS di satu tempat, aplikasi tidak perlu port publik, ganti aplikasi tanpa mengubah DNS, log terpusat.

proxy_pass http://127.0.0.1:3000; mengirim request ke backend. Tanpa proxy_set_header, aplikasi kehilangan informasi penting:

HeaderGunanya
HostAplikasi tahu domain yang diminta (penting untuk cookie, redirect)
X-Real-IPIP klien asli
X-Forwarded-ForRantai IP klien
X-Forwarded-ProtoSkema asli (http/https)

WebSocket butuh header Upgrade dan Connection yang di-set dari request klien. Karena Connection harus bernilai upgrade hanya saat ada Upgrade, dipakai map.

Praktik

  1. Siapkan backend sederhana untuk latihan.
mkdir -p ~/apps/api && cat > ~/apps/api/server.py <<'PY'
from http.server import BaseHTTPRequestHandler, HTTPServer
import json, os

class H(BaseHTTPRequestHandler):
    def do_GET(self):
        body = json.dumps({
            "path": self.path,
            "host": self.headers.get("Host"),
            "real_ip": self.headers.get("X-Real-IP"),
            "proto": self.headers.get("X-Forwarded-Proto"),
        }).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        self.wfile.write(body)

HTTPServer(("127.0.0.1", 3000), H).serve_forever()
PY
python3 ~/apps/api/server.py &   # untuk latihan; di produksi pakai systemd
curl -s http://127.0.0.1:3000/cek
  1. Konfigurasi reverse proxy.
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      '';      # string kosong: header Connection tidak diubah, keepalive upstream tetap jalan
}

upstream app_backend {
    server 127.0.0.1:3000;
    keepalive 16;
}

server {
    listen 80;
    server_name app.example.com;

    location / {
        proxy_pass http://app_backend;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        proxy_connect_timeout 5s;
        proxy_send_timeout    60s;
        proxy_read_timeout    60s;
        proxy_buffering       off;   # untuk SSE/streaming
    }
}

Catatan: map harus berada di dalam blok http, bukan di dalam server. Letakkan di /etc/nginx/conf.d/proxy-map.conf.

  1. Terapkan dan uji.
sudo nginx -t && sudo systemctl reload nginx
curl -s -H 'Host: app.example.com' http://127.0.0.1/ | python3 -m json.tool
curl -s -H 'Host: app.example.com' -H 'X-Forwarded-Proto: https' http://127.0.0.1/cek
  1. Pastikan backend tidak terbuka ke internet.
sudo ss -tulpn | grep 3000        # harus 127.0.0.1:3000, bukan 0.0.0.0:3000
  1. Ganti backend tanpa menyentuh klien: ubah server di upstream, nginx -t, reload.

Pelajaran 2.7 — HTTPS dengan Let's Encrypt

Tujuan

Menerbitkan sertifikat, memasangnya di Nginx, dan memastikan perpanjangan otomatis berjalan.

Konsep

Let's Encrypt memvalidasi kepemilikan domain lewat HTTP-01: server harus menjawab http://domain/.well-known/acme-challenge/... pada port 80. Karena itu port 80 wajib terbuka dan DNS harus sudah benar sebelum meminta sertifikat.

Certbot dengan plugin Nginx mengubah konfigurasi secara otomatis, lalu memasang timer systemd untuk perpanjangan.

Praktik

  1. Prasyarat.
dig +short app.example.com        # harus IP server
sudo ufw status | grep -E '80|443'
sudo systemctl is-active nginx
  1. Pasang certbot.
sudo apt install -y certbot python3-certbot-nginx
  1. Terbitkan sertifikat (pastikan server_name sudah benar).
sudo certbot --nginx -d app.example.com --redirect --agree-tos -m admin@example.com --no-eff-email
# tambahkan `-d www.app.example.com` HANYA jika server_name untuk www memang sudah ada
# di Nginx; domain tanpa server block membuat validasi gagal.
  1. Verifikasi hasil.
curl -sI https://app.example.com | head -3
curl -s -o /dev/null -w '%{http_code}\n' http://app.example.com    # harus 301
echo | openssl s_client -connect app.example.com:443 -servername app.example.com 2>/dev/null | openssl x509 -noout -subject -dates
  1. Perpanjangan otomatis.
systemctl list-timers | grep certbot
sudo certbot renew --dry-run
  1. HSTS dan header keamanan tambahan.
sudo nano /etc/nginx/snippets/security-headers.conf
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
# di dalam server block 443
include /etc/nginx/snippets/security-headers.conf;

Peringatan: includeSubDomains pada HSTS berarti semua subdomain wajib HTTPS. Jangan aktifkan sebelum semua subdomain siap.

  1. Perbarui sertifikat manual (kalau perlu setelah DNS berubah).
sudo certbot renew --force-renewal

Pelajaran 2.8 — Load balancing, proteksi, dan tuning produksi

Tujuan

Membagi beban ke beberapa backend dan melindungi aplikasi dari lonjakan serta pengunjung kasar.

Konsep

upstream adalah daftar backend. Metode: round-robin (default), least_conn (ke koneksi paling sedikit), ip_hash (klien sama ke backend sama, untuk sesi tanpa shared state).

limit_req_zone membatasi laju request per IP. Batas ini didefinisikan di blok http dan dipakai di location dengan limit_req.

client_max_body_size mengatur ukuran body maksimum; default 1 MB adalah penyebab tersembunyi error 413 saat upload.

Praktik

  1. Upstream dan metode.
upstream app_backend {
    least_conn;
    server 127.0.0.1:3000 max_fails=3 fail_timeout=10s;
    server 127.0.0.1:3001 max_fails=3 fail_timeout=10s backup;
    keepalive 16;
}
  1. Rate limit.
sudo nano /etc/nginx/conf.d/limits.conf
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conn_limit:10m;
location /api/ {
    limit_req zone=api_limit burst=20 nodelay;
    limit_conn conn_limit 20;
    proxy_pass http://app_backend;
}
  1. Basic auth (misalnya untuk halaman admin).
sudo apt install -y apache2-utils

Latihan

  1. Tambahkan backend kedua di port berbeda, buktikan round-robin dengan melihat log akses dua backend.
  2. Pasang rate limit 5r/s dengan burst=10 dan buktikan dengan for i in $(seq 1 30); do curl -s -o /dev/null -w '%{http_code} ' http://127.0.0.1/api/; done.

Kriteria selesai: error 413 pada upload hilang setelah client_max_body_size dinaikkan, dan kamu bisa menjelaskan tiap baris pada blok location /api/.

Cek pemahaman

  1. Kapan ip_hash diperlukan? — Saat sesi pengguna disimpan di memori satu backend, tanpa penyimpanan bersama.
  2. Apa fungsi burst pada limit_req? — Mengizinkan lonjakan sesaat di atas laju rata-rata sebelum menolak.
  3. Kenapa keepalive pada upstream menghemat sumber daya? — Koneksi ke backend dipakai ulang, tidak membuat koneksi TCP baru tiap request.

Tugas untuk pertemuan berikutnya

Kerjakan: Tambahkan upstream dua backend, limit_req 10r/s dengan burst=20, dan basic auth untuk /admin/.

Siapkan: Uji dengan 30 request beruntun dan simpan log distribusinya.

Bawa bukti: Bukti distribusi request ke dua backend + respons 429 saat batas terlampaui + curl 401 pada /admin/.

Proyek mini modul

Publikasikan satu aplikasi di 127.0.0.1:3000 sebagai https://app.example.com:

  1. Jalankan aplikasi (boleh skrip latihan pelajaran 2.6) lewat systemd, listen di 127.0.0.1:3000.
  2. Buat server block app.example.com dengan reverse proxy lengkap: Host, X-Real-IP, X-Forwarded-For, X-Forwarded-Proto, dukungan WebSocket.
  3. Tambahkan redirect HTTP→HTTPS dan location = /health yang membalas 200 ok.
  4. Terbitkan sertifikat Let's Encrypt, buktikan certbot renew --dry-run sukses.
  5. Tambahkan limit_req 10r/s burst=20, client_max_body_size 25m, dan header keamanan.
  6. Buktikan port 3000 tidak bisa diakses dari luar server (nc -zv IP 3000 dari laptop harus gagal).
  7. Tulis catatan-nginx.md: file konfigurasi yang dipakai, perintah reload, dan cara membaca log.

Kriteria selesai: curl -sI https://app.example.com mengembalikan 200, curl -s -o /dev/null -w '%{http_code}' http://app.example.com mengembalikan 301, dan sudo nginx -t bersih.

Config contoh lengkap

Satu file /etc/nginx/nginx.conf utuh yang siap pakai untuk skenario modul ini (statis example.com + reverse proxy app.example.com). Blok-blok terpisah di pelajaran sebelumnya adalah potongan dari file ini. Sudah diuji dengan nginx -t.

# /etc/nginx/nginx.conf
# Konfigurasi Nginx utuh untuk Ubuntu 24.04 LTS (Nginx 1.24.x dari repo Ubuntu).
# Skenario Modul 2: example.com (statis) + app.example.com (reverse proxy) di 203.0.113.10.
# Semua direktif di bawah ada di dokumentasi resmi Nginx (lihat bagian Referensi).

user  www-data;                          # worker berjalan sebagai user tanpa hak root
worker_processes auto;                   # satu worker per core CPU
pid /run/nginx.pid;                      # lokasi file PID master process
error_log /var/log/nginx/error.log warn; # log error global, level warn

include /etc/nginx/modules-enabled/*.conf;   # modul dinamis dari paket distro

events {
    worker_connections 1024;             # koneksi simultan per worker
    multi_accept on;                     # terima beberapa koneksi sekaligus
}

http {
    ## --- Dasar ---
    sendfile on;                         # kirim file langsung dari kernel
    tcp_nopush on;                       # gabungkan header dengan awal body
    tcp_nodelay on;                      # jangan tunda paket kecil saat keepalive
    keepalive_timeout 65;                # lama koneksi client dibiarkan terbuka
    types_hash_max_size 2048;
    server_tokens off;                   # sembunyikan versi Nginx di header Server

    include /etc/nginx/mime.types;       # peta ekstensi -> MIME type
    default_type application/octet-stream;

    ## --- Logging ---
    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for"';
    access_log /var/log/nginx/access.log main;

    ## --- TLS untuk semua server block 443 ---
    ssl_protocols TLSv1.2 TLSv1.3;       # buang TLS 1.0/1.1 yang sudah tidak aman
    ssl_prefer_server_ciphers off;       # biarkan client memilih cipher tercepat
    ssl_session_cache shared:SSL:10m;    # cache sesi TLS antar worker
    ssl_session_timeout 1d;              # masa berlaku cache sesi

    ## --- Kompresi ---
    gzip on;                             # aktifkan gzip
    gzip_vary on;                        # kirim Vary: Accept-Encoding
    gzip_proxied any;                    # tetap kompres response dari backend
    gzip_comp_level 5;                   # keseimbangan CPU vs rasio kompresi
    gzip_min_length 1000;                # response < 1 KB tidak sepadan dikompres
    gzip_types text/plain text/css text/xml application/json
               application/javascript application/xml application/xml+rss
               image/svg+xml;            # text/html selalu dikompres, tidak perlu didaftar

    ## --- Rate limit (zone wajib di konteks http) ---
    limit_req_zone $binary_remote_addr zone=per_ip:10m rate=10r/s;
    limit_req_zone $binary_remote_addr zone=login_ip:10m rate=1r/s;
    limit_req_status 429;                # status saat ditolak (default 503)
    limit_req_log_level warn;

    ## --- Helper WebSocket ---
    map $http_upgrade $connection_upgrade {
        default upgrade;                 # ada header Upgrade -> teruskan
        ''      '';                      # tidak ada -> biarkan header apa adanya (keepalive utuh)
    }

    ## --- Grup backend aplikasi ---
    upstream app_nodes {
        least_conn;                      # pilih node dengan koneksi aktif tersedikit
        server 127.0.0.1:3000 max_fails=3 fail_timeout=15s;
        server 127.0.0.1:3001 max_fails=3 fail_timeout=15s;
        keepalive 16;                    # pakai ulang koneksi TCP ke backend
    }

    ## --- Penangkap request tak dikenal ---
    server {
        listen 80 default_server;        # blok default untuk IPv4
        listen [::]:80 default_server;   # dan IPv6
        server_name _;                   # nama dummy, bukan domain nyata
        return 444;                      # tutup koneksi tanpa balasan
    }

    ## --- Redirect HTTP -> HTTPS untuk semua domain ---
    server {
        listen 80;
        listen [::]:80;
        server_name example.com www.example.com app.example.com;
        location /.well-known/acme-challenge/ {
            root /var/www/html;          # biarkan certbot menaruh file challenge
        }
        location / {
            return 301 https://$host$request_uri;
        }
    }

    ## --- example.com: situs statis ---
    server {
        listen 443 ssl http2;            # Nginx 1.24: HTTP/2 lewat parameter listen.
        listen [::]:443 ssl http2;       # Di 1.25.1+ tulis `listen 443 ssl;` + `http2 on;`
        server_name example.com;

        ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

        add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
        add_header X-Content-Type-Options "nosniff" always;
        add_header X-Frame-Options "SAMEORIGIN" always;
        add_header Referrer-Policy "strict-origin-when-cross-origin" always;

        root /var/www/static.example.com;
        index index.html;

        access_log /var/log/nginx/static.example.com.access.log main;
        error_log  /var/log/nginx/static.example.com.error.log warn;

        location / {
            try_files $uri $uri/ =404;   # coba file, coba direktori, kalau gagal 404
        }

        location = /health {
            default_type text/plain;
            return 200 "ok\n";           # health check murah, tidak menyentuh disk
        }

        error_page 404 /404.html;
        error_page 500 502 503 504 /50x.html;
        location = /404.html { internal; }    # hanya lewat error_page
        location = /50x.html { internal; }
    }

    ## --- www -> non-www (kanonik: example.com) ---
    server {
        listen 443 ssl http2;
        listen [::]:443 ssl http2;
        server_name www.example.com;

        ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

        return 301 https://example.com$request_uri;
    }

    ## --- app.example.com: reverse proxy ke 127.0.0.1:3000/3001 ---
    server {
        listen 443 ssl http2;
        listen [::]:443 ssl http2;
        server_name app.example.com;

        ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;

        client_max_body_size 25m;        # batas body request; default hanya 1m
        server_tokens off;

        add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
        add_header X-Content-Type-Options "nosniff" always;
        add_header X-Frame-Options "SAMEORIGIN" always;
        add_header Referrer-Policy "strict-origin-when-cross-origin" always;

        access_log /var/log/nginx/app.example.com.access.log main;
        error_log  /var/log/nginx/app.example.com.error.log warn;

        # Aset statis dilayani Nginx, tidak mengganggu aplikasi
        location ^~ /static/ {
            root /var/www/app.example.com;
            expires 30d;
            add_header Cache-Control "public, immutable";
            access_log off;
        }

        location = /favicon.ico { return 204; }

        # Admin: basic auth + rate limit. Hanya layak di atas HTTPS.
        location /admin/ {
            auth_basic           "Area admin";
            auth_basic_user_file /etc/nginx/.htpasswd;
            limit_req zone=per_ip burst=10 nodelay;

            proxy_pass http://app_nodes;
            proxy_http_version 1.1;
            proxy_set_header Connection        "";   # kosong agar keepalive upstream aktif
            proxy_set_header Host              $host;
            proxy_set_header X-Real-IP         $remote_addr;
            proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }

        # Login: rate limit ketat untuk menahan brute force
        location = /login {
            limit_req zone=login_ip burst=3 nodelay;

            proxy_pass http://app_nodes;
            proxy_http_version 1.1;
            proxy_set_header Connection        "";
            proxy_set_header Host              $host;
            proxy_set_header X-Real-IP         $remote_addr;
            proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }

        # WebSocket: Upgrade/Connection adalah header hop-by-hop, harus di-set manual
        location /ws/ {
            proxy_pass http://app_nodes;
            proxy_http_version 1.1;
            proxy_set_header Upgrade           $http_upgrade;
            proxy_set_header Connection        $connection_upgrade;
            proxy_set_header Host              $host;
            proxy_read_timeout 3600s;
            proxy_send_timeout 3600s;
        }

        # Upload: body besar, diteruskan streaming tanpa ditulis ke disk dulu
        location /upload {
            client_max_body_size 100m;
            proxy_pass http://app_nodes;
            proxy_http_version 1.1;
            proxy_request_buffering off;
            proxy_read_timeout 300s;
            proxy_set_header Host              $host;
            proxy_set_header X-Real-IP         $remote_addr;
            proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }

        # Sisanya ke aplikasi
        location / {
            limit_req zone=per_ip burst=20 nodelay;

            proxy_pass http://app_nodes;         # tanpa URI -> path dikirim apa adanya
            proxy_http_version 1.1;              # default 1.0 di 1.24; wajib 1.1 untuk keepalive
            proxy_set_header Connection        "";
            proxy_set_header Host              $host;                          # domain asli, bukan upstream
            proxy_set_header X-Real-IP         $remote_addr;                   # IP client asli
            proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;     # rantai proxy
            proxy_set_header X-Forwarded-Proto $scheme;                        # https, bukan http

            proxy_connect_timeout 5s;            # gagal sambung cepat -> 502
            proxy_send_timeout    60s;
            proxy_read_timeout    60s;           # backend terlalu lama -> 504

            proxy_buffering on;                  # serap response backend ke buffer
            proxy_buffers 16 16k;
            proxy_buffer_size 16k;
        }

        error_page 404 /404.html;
        error_page 500 502 503 504 /50x.html;
        location = /404.html { internal; root /var/www/app.example.com; }
        location = /50x.html { internal; root /var/www/app.example.com; }
    }
}

sudo cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.bak   # selalu backup dulu

Ringkasan modul

Sampai sini aplikasi jalan langsung di server: rawan beda versi, susah di-rollback, dan sulit dipindah. Docker mengemas aplikasi beserta dependensinya menjadi image, lalu menjalankannya sebagai container.

Asumsi: Ubuntu 24.04 LTS, Docker Engine dari repository resmi Docker (docker-ce), Docker Compose v2 (docker compose, bukan docker-compose). Aplikasi contoh: API kecil yang listen di 0.0.0.0:3000 di dalam container.

Hasil pembelajaran

  • Menjelaskan perbedaan image, container, dan registry, serta kapan container bukan pilihan tepat.
  • Memasang Docker dari repository resmi dan menjelaskan risiko bergabung ke grup docker.
  • Menulis Dockerfile multi-stage yang menghasilkan image kecil dan berjalan sebagai user non-root.
  • Mengelola data dengan volume dan konfigurasi dengan env file tanpa menaruh rahasia di image.
  • Menghubungkan container ke database dan ke Nginx di host lewat network dan port publish.
  • Menjalankan aplikasi plus database dengan satu perintah docker compose up -d.
  • Mendiagnosis container yang langsung mati, port bentrok, dan volume yang menutupi data.

Pelajaran 3.1 — Kenapa container

Tujuan

Memahami masalah yang dipecahkan container, dan kapan sebaiknya tidak memakainya.

Konsep

IstilahArti
ImagePaket read-only berisi aplikasi + dependensi + metadata
ContainerProses yang berjalan dari image, punya filesystem dan network sendiri
RegistryTempat menyimpan image (Docker Hub, GHCR)
VolumePenyimpanan persisten di luar siklus hidup container

Container berbagi kernel host, jadi jauh lebih ringan dari VM yang menjalankan sistem operasi penuh. Ini juga berarti isolasi container lebih lemah daripada VM — masalah keamanan kernel berdampak ke semua container.

Masalah "di laptop saya jalan" hilang karena image membawa semua dependensi. Deploy jadi: bangun image, dorong ke registry, tarik di server, jalankan.

Kapan tidak memakai Docker: aplikasi tunggal yang sederhana dan sudah stabil dengan systemd; kebutuhan kernel kustom atau akses perangkat khusus; tim kecil yang belum siap merawat registry dan pipeline. Docker menambah lapisan yang harus dipahami, bukan menghilangkannya.

Praktik

  1. Lihat perbedaan ukuran dan isolasi.
uname -r                                  # kernel yang dibagi semua container
docker run --rm alpine uname -r           # kernel yang sama di dalam container
docker run --rm alpine cat /etc/os-release | head -2   # OS di dalam container beda dari host
  1. Alur hidup sebuah image.
docker pull nginx:1.27-alpine
docker images
docker run -d --name web nginx:1.27-alpine
docker ps
docker exec -it web nginx -v
docker rm -f web
docker rmi nginx:1.27-alpine
  1. Container itu proses, bukan mesin.
docker run -d --name web nginx:1.27-alpine
ps aux | grep -c nginx        # proses container terlihat di host
docker rm -f web

Kalau error

GejalaPenyebabSolusi
Bingung image vs containerAnalogi yang salahImage = cetakan, container = hasil jalan dari cetakan
Data hilang setelah container dihapusData disimpan di layer containerPakai volume (pelajaran 3.6)

Latihan

  1. Jalankan alpine dan buktikan kernelnya sama dengan host tetapi OS-nya berbeda.
  2. Jelaskan dalam tiga kalimat kenapa container cocok untuk aplikasi web dan kurang cocok untuk menjalankan database besar.

Kriteria selesai: kamu bisa menjelaskan beda image, container, dan volume tanpa melihat catatan.

Cek pemahaman

  1. Apa yang tidak dibagi container dengan host? — Filesystem, network namespace, dan proses (isolasinya), meski kernel dibagi.
  2. Di mana image disimpan secara default? — Di registry seperti Docker Hub atau GHCR, dan salinannya di cache lokal server.

Tugas untuk pertemuan berikutnya

Kerjakan: Tulis container-vs-vm.md: 5 kalimat perbandingan dan 2 kondisi nyata ketika container bukan pilihan tepat.

Siapkan: Jalankan satu container dan bandingkan uname -r di host dan di dalam container.

Bawa bukti: Isi catatan + output uname -r dari keduanya.

Pelajaran 3.2 — Instalasi dan verifikasi

Tujuan

Memasang Docker Engine dari repository resmi dan memahami konsekuensi grup docker.

Konsep

Paket docker.io dari Ubuntu sering tertinggal versi. Untuk server, pakai docker-ce dari download.docker.com.

Grup docker memberi hak setara root: anggota grup bisa me-mount seluruh filesystem host ke dalam container. Di server produksi, batasi siapa yang masuk grup ini — atau pakai rootless Docker.

Praktik

  1. Pasang dari repository resmi.
sudo apt update && sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings

Pelajaran 3.5 — Image kecil dan aman

Tujuan

Menghasilkan image produksi: multi-stage, non-root, versi ter-pin, tanpa rahasia.

Konsep

Multi-stage build memakai beberapa FROM: satu tahap untuk membangun (compiler, dev dependencies, bundler), satu tahap akhir yang hanya menyalin hasilnya memakai COPY --from=<tahap>. Tahap build tetap tertinggal di cache dan tidak masuk image akhir, sehingga image lebih kecil dan permukaan serangan menyusut. Tahap build yang tidak pernah di-COPY --from adalah tahap mati: ia hanya memboroskan waktu build.

Menjalankan sebagai root di dalam container berarti bug di aplikasi bisa berujung pada akses root ke host (terutama bila ada volume yang di-mount). Pakai USER non-root.

Rahasia tidak boleh ada di image: layer image bisa dibaca siapa pun yang punya image-nya. Rahasia diberikan saat runtime lewat environment variable atau file yang di-mount.

Praktik

ENV NODE_ENV=production
WORKDIR /app

COPY --from=build /app/node_modules ./node_modules   # inilah yang membuat tahap build berguna
COPY package.json server.js ./

# Jalankan sebagai user non-root bawaan image node
USER node

EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"

docker rm -f db api

docker network ls

Pelajaran 3.8 — Docker Compose

Tujuan

Menjalankan aplikasi, database, dan konfigurasinya dengan satu file dan satu perintah.

Konsep

Compose mendeskripsikan beberapa service dalam satu compose.yaml. Setiap service bisa punya image, port, volume, environment, dan healthcheck. depends_on dengan condition: service_healthy menunggu database siap sebelum aplikasi mulai.

restart: unless-stopped membuat container hidup lagi setelah reboot, kecuali kamu sengaja menghentikannya.

Praktik

  1. File Compose lengkap.
cd ~/apps/node-api
cat > compose.yaml <<'YAML'
services:
  api:
    build: .
    image: node-api:2.0.0
    restart: unless-stopped
    env_file: .env
    environment:
      DB_HOST: db
      DB_PORT: "5432"
      DB_NAME: appdb
      DB_USER: appuser
    ports:
      - "127.0.0.1:3000:3000"
    depends_on:
      db:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 30s
      timeout: 3s
      retries: 3
    networks: [appnet]

  db:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD wajib diisi}
    volumes:
      - dbdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks: [appnet]

volumes:
  dbdata:

networks:
  appnet:
    driver: bridge
YAML

Catatan: pastikan DB_PASSWORD ada di .env, dan DB_USER/DB_NAME di .env konsisten dengan nilai di atas.

  1. Jalankan dan periksa.
docker compose config --quiet && echo "YAML valid"
docker compose up -d
docker compose ps
docker compose logs -f --tail 30 api

Pelajaran 4.1 — Konsep CI/CD dan komponen Actions

Tujuan

Memahami alur kerja Actions sebelum menulis YAML.

Konsep

IstilahArti
CI (continuous integration)Setiap perubahan otomatis diuji dan dibangun
Continuous deliverySetiap build siap dirilis, rilis dipicu manual
Continuous deploymentSetiap perubahan yang lulus langsung dirilis

Komponen:

  • Workflow — satu file YAML di .github/workflows/.
  • Event (on) — pemicu: push, pull_request, schedule, workflow_dispatch.
  • Job — kumpulan step yang berjalan di satu runner; job default paralel.
  • Step — satu langkah: uses (memakai action) atau run (perintah shell).
  • Runner — mesin yang menjalankan job (ubuntu-24.04, ubuntu-latest, self-hosted).
  • Action — komponen siap pakai dari Marketplace, dipanggil dengan uses: owner/repo@versi.

Runner GitHub bersifat sementara: setiap job mulai dari VM bersih. Karena itu jangan mengandalkan file yang tersisa dari job sebelumnya.

Praktik

  1. Lihat paket gratis dan menit yang terpakai: repo → Settings → Billing (atau halaman Actions usage). Repo publik tidak memakai kuota.
  1. Buat workflow pertama yang bisa dipicu manual.
mkdir -p .github/workflows
cat > .github/workflows/hello.yml <<'YAML'
name: Hello

on:
  workflow_dispatch:

jobs:
  info:
    runs-on: ubuntu-24.04
    steps:
      - name: Tampilkan informasi runner
        run: |
          uname -a
          docker --version
          echo "repo=$GITHUB_REPOSITORY ref=$GITHUB_REF"
YAML
git add .github/workflows/hello.yml && git commit -m "ci: workflow hello" && git push
  1. Jalankan dari tab Actions → pilih workflow → Run workflow. Baca log tiap step.
  1. Kenali variabel bawaan yang sering dipakai: GITHUB_SHA, GITHUB_REF_NAME, GITHUB_REPOSITORY, GITHUB_ACTOR, RUNNER_OS.

Kalau error

unable to resolve action owner/repo@vNVersi major action berubah / tag dihapusCek versi terbaru di GitHub Marketplace, ganti @vN sesuai

  2. Sebutkan tiga perbedaan runner GitHub dengan server produksimu.

  3. Apa fungsi uses? — Memanggil action siap pakai, bukan perintah shell.

Tugas untuk pertemuan berikutnya

Kerjakan: Buat workflow workflow_dispatch yang mencetak GITHUB_SHA, GITHUB_REF_NAME, dan versi Docker di runner.

Siapkan: Baca log run tersebut sampai selesai dan catat nama tiap step.

Bawa bukti: Tangkapan layar run hijau + daftar step + jawaban: kenapa job tidak boleh bergantung pada file dari job lain?

Pelajaran 4.2 — Workflow pertama

Tujuan

Menulis YAML yang benar dan tahu cara membacanya saat gagal.

Konsep

Struktur minimum:

name: Nama
on: [push]
jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - run: echo "halo"

YAML sensitif terhadap indentasi spasi (bukan Tab). Kesalahan paling sering: indentasi salah, titik dua hilang, atau on: ditulis On:.

actions/checkout wajib dipanggil lebih dulu kalau step butuh isi repo. Tanpa itu, direktori kerja kosong.

Praktik

  1. Workflow CI dasar.
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4

      - name: Pasang Node
        uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm

      - name: Pasang dependensi
        run: npm ci

      - name: Jalankan lint
        run: npm run lint --if-present

      - name: Jalankan test
        run: npm test --if-present
  1. Validasi YAML sebelum push (tanpa Actions sekalipun).
python3 -c "import yaml,sys; yaml.safe_load(open('.github/workflows/ci.yml')); print('YAML valid')" 2>/dev/null || \
  node -e "const fs=require('fs');console.log('cek manual: indentasi konsisten')"
  1. Melihat log: tab Actions → pilih run → klik job → klik step. Baris merah menandai perintah yang gagal; exit code tercatat.
  1. Debug lokal sebelum push.
npm ci
npm test
docker build -t node-api:local .

Memperbaiki di lokal jauh lebih cepat daripada bolak-balik lewat runner.

Tugas untuk pertemuan berikutnya

Kerjakan: Buat workflow CI yang berjalan pada push ke main dan semua pull_request: checkout, setup, install, test.

Siapkan: Sengaja buat satu test gagal di branch terpisah, lalu perbaiki.

Bawa bukti: Dua tautan run: satu merah (gagal) dan satu hijau, plus step mana yang gagal pada run merah.

Pelajaran 4.3 — Test dan lint otomatis

Tujuan

Menjalankan pengujian di beberapa versi sekaligus dan menahan perubahan yang gagal.

Konsep

Matrix menjalankan job yang sama dengan kombinasi variabel berbeda. fail-fast: false membuat kombinasi lain tetap jalan walau satu gagal — berguna untuk melihat gambaran lengkap.

Branch protection memakai hasil job sebagai syarat merge: pull request tidak bisa digabung sebelum status check hijau.

Praktik

  1. Matrix build.
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-24.04
    strategy:
      fail-fast: false
      matrix:
        node: ['20', '22']
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci
      - run: npm test --if-present
  1. Job terpisah untuk lint dan test (paralel, lebih cepat terlihat).
jobs:
  lint:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: npm }
      - run: npm ci
      - run: npx --yes eslint . || true   # jangan `|| true` di produksi sungguhan

  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: npm }
      - run: npm ci
      - run: npm test

Catatan: || true membuat langkah selalu hijau. Hanya dipakai saat memperkenalkan lint ke kode lama, dan harus dihapus setelah bersih.

  1. Jadikan syarat merge: repo → Settings → Branches → Add branch protection rule untuk main → aktifkan Require status checks to pass → pilih nama job (test).
  1. Untuk Python (sesuaikan bila proyekmu Python).
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: pip
      - run: pip install -r requirements.txt
      - run: pytest -q

Kalau error

GejalaPenyebabSolusi
Build matrix memakan waktu lamaCache tidak aktifAktifkan cache: pada setup action
npm ci gagal hanya di satu versi NodeKetidakcocokan dependensiPin engines di package.json atau perbaiki kode
Status check tidak muncul di PRNama job berubah, atau workflow belum berjalan di branch ituSamakan nama job dengan yang didaftarkan di branch protection

Latihan

  1. Tambahkan matrix dua versi Node dan buktikan keduanya berjalan.
  2. Aktifkan branch protection pada main dan buktikan PR tidak bisa di-merge saat test merah.

Kriteria selesai: pull request menampilkan status check dari workflow-mu.

Cek pemahaman

  1. Apa fungsi cache: npm? — Menyimpan cache dependensi antar-run agar npm ci lebih cepat.
  2. Kenapa fail-fast: false berguna? — Melihat semua kombinasi yang gagal, bukan hanya yang pertama.

Tugas untuk pertemuan berikutnya

Kerjakan: Tambahkan matrix dua versi bahasa, aktifkan cache dependensi, dan pasang branch protection yang mewajibkan status check hijau.

Siapkan: Buat pull request yang sengaja gagal dan buktikan tombol merge terkunci.

Bawa bukti: Tangkapan layar status check di PR + perbandingan waktu run dengan dan tanpa cache.

Tujuan

Menyimpan kredensial dengan benar dan memberi token izin seminimal mungkin.

Konsep

secrets.*Terenkripsi, tidak bisa dibaca setelah disimpan, otomatis di-mask di log

GITHUB_TOKEN adalah cara paling aman mengakses registry dan API GitHub: tidak perlu Personal Access Token, dan masa berlakunya hanya selama run.

Jangan pernah mencetak secret ke log. Masking bekerja untuk nilai yang persis, tetapi nilai yang di-encode atau dipotong bisa lolos — jadi jangan dicetak sama sekali.

Praktik

  1. Pakai di workflow.
    steps:

          echo "host=${{ vars.DEPLOY_HOST }}"
          echo "user=${{ secrets.SSH_USER }}"        # hindari contoh seperti ini di kode sungguhan

jobs:
  deploy:
    runs-on: ubuntu-24.04
    environment:
      name: production
      url: https://app.example.com
    steps:
      - run: echo "deploy ke production"

Buat environment production di Settings → Environments, tambahkan Required reviewers, dan batasi deployment branch ke main.

  1. permissions minimum per workflow.
permissions:
  contents: read

Naikkan hanya di job yang butuh, misalnya untuk mendorong image:

jobs:
  publish:
    permissions:
      contents: read
      packages: write

Pelajaran 4.5 — Build dan push image ke GHCR

Tujuan

Menghasilkan image ber-tag yang bisa dilacak dan di-rollback.

Konsep

GHCR (ghcr.io) menerima login memakai GITHUB_TOKEN sebagai username ${{ github.actor }}. Butuh packages: write.

Strategi tag yang sehat:

TagGunanya
sha-<commit>Presisi untuk rollback
latestKenyamanan; tidak dipakai sebagai satu-satunya acuan deploy
<git tag>Untuk rilis resmi

Cache build memakai type=gha sehingga build berikutnya jauh lebih cepat.

Praktik

  1. Workflow build & push.
name: Build and push

on:
  push:
    branches: [main]
    tags: ['v*']
  workflow_dispatch:

env:
  IMAGE: ghcr.io/${{ github.repository }}

jobs:
  build:
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - name: Login ke GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Siapkan metadata tag
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=sha,prefix=sha-,format=long   # 40 hex, sama dengan workflow_run.head_sha
            type=ref,event=branch
            type=semver,pattern={{version}}

      - name: Build dan push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
  1. Verifikasi hasil: repo → tab Packages → pilih image → lihat tag dan ukuran.
  1. Uji tarik image di server.
echo "$GHCR_TOKEN" | docker login ghcr.io -u USERNAME --password-stdin
# tag sha panjang (40 karakter) bila metadata memakai format=long
docker pull "ghcr.io/USER/REPO:sha-$(git rev-parse HEAD)"

Catatan: bila package diset private, server butuh kredensial untuk menariknya. Untuk repo publik, image juga bisa dibuat publik.

  1. Rollback dengan tag sha: identifikasi tag sebelumnya di tab Packages.

Kalau error

denied: installation not allowed to Write organization packagepackages: write tidak adaTambahkan blok permissions di job
unauthorized saat loginMemakai password akun, bukan tokenPakai ${{ secrets.GITHUB_TOKEN }}

  1. Push ke main, buktikan image muncul di Packages dengan tag sha-....
  2. Bandingkan waktu build pertama dan kedua; tunjukkan efek cache.

Cek pemahaman

  1. Kenapa tag sha lebih penting daripada latest? — Menunjuk image persis, memungkinkan rollback deterministik.
  2. Kenapa permissions diletakkan di level job, bukan workflow? — Least privilege: hanya job yang butuh yang mendapat izin tulis.

Tugas untuk pertemuan berikutnya

Pelajaran 4.6 — Deploy ke VPS lewat SSH

Tujuan

Menerapkan image baru di server tanpa interaksi manual.

Konsep

Alur deploy yang dapat diulang:

  1. Runner menarik image baru dengan tag spesifik.
  2. Mengganti versi image di server (lewat image tag di .env).
  3. Recreate container.
  4. Menjalankan health check.
  5. Gagal → kembali ke tag sebelumnya.

Server tidak membangun image. Server hanya menarik dan menjalankan — build di runner, jalankan di server.

Kunci SSH khusus deploy: satu key pair, hanya untuk pipeline, tanpa passphrase, disimpan sebagai secret. Public key-nya ditaruh di ~/.ssh/authorized_keys milik user deploy.

Praktik

  1. Siapkan key khusus deploy.
ssh-keygen -t ed25519 -C "gha-deploy" -f ~/.ssh/gha_deploy -N ""
cat ~/.ssh/gha_deploy.pub    # tempel ke server
ssh-copy-id -i ~/.ssh/gha_deploy.pub deploy@203.0.113.10

Pelajaran 4.7 — Deploy aman dan rollback

Tujuan

Membuat deploy bisa gagal dengan aman, dan bisa dibalik cepat.

Konsep

  • Deploy hanya dari main (atau tag rilis), tidak dari PR.
  • concurrency mencegah dua deploy berjalan bersamaan.
  • Health check + smoke test menentukan sukses/gagal.
  • Rollback = deploy ulang tag sebelumnya, bukan memperbaiki di server.

Praktik

  1. Skrip deploy dengan rollback.

cd "$(dirname "$0")"

set_image() {
  if grep -q '^IMAGE=' .env; then
    sed -i "s|^IMAGE=.*|IMAGE=$1|" .env
  else
    echo "IMAGE=$1" >> .env
  fi
}

  fi
  sleep 3
done

docker compose logs --tail 50 api >&2 || true
if [ -n "$PREV_IMAGE" ]; then
  set_image "$PREV_IMAGE"
  docker compose up -d --remove-orphans
fi
exit 1

Tujuan

Menghilangkan duplikasi dan menambah visibilitas tanpa menambah kerumitan.

Konsep

Pelajaran 5.4 — Pipeline CI/CD

Tujuan

Membuat deploy berjalan otomatis dari git push.

Langkah

  1. .github/workflows/ci.yml — test + lint, berjalan pada PR dan push ke main.

Pelajaran 5.5 — Go-live dan observability

Tujuan

Menjalankan rilis dengan bukti, bukan dengan harapan.

Checklist go-live

  • [ ] DNS mengarah ke server, dig +short sesuai.
  • [ ] Nginx lolos nginx -t, service aktif dan enabled.
  • [ ] Sertifikat valid > 30 hari, certbot renew --dry-run sukses, timer aktif.
  • [ ] Firewall hanya membuka 22/80/443; port backend tertutup dari internet — dibuktikan dengan nc -zv <IP> 3000 dari luar, bukan hanya dari ufw status (Docker melewati ufw).
  • [ ] docker compose ps menunjukkan semua service running/healthy.
  • [ ] Health check lokal dan publik membalas 200.
  • [ ] Log akses dan error Nginx terisi; docker compose logs bersih dari error berulang.
  • [ ] .env mode 600, tidak ada rahasia di repo maupun image.
  • [ ] Backup database terjadwal dan sudah pernah dipulihkan sekali.
  • [ ] Rollback terbukti berjalan (diuji di staging atau saat latihan).
  • [ ] Deploy hanya bisa dipicu dari branch main.

Checklist keamanan dasar

  • [ ] SSH key-only, PermitRootLogin no, user deploy tanpa sudo penuh bila memungkinkan.
  • [ ] Tidak ada service yang listen di 0.0.0.0 selain 22/80/443.
  • [ ] Image memakai tag versi, bukan latest saja, dan berjalan sebagai non-root.
  • [ ] Secret hanya di GitHub Secrets dan .env server.
  • [ ] Login GHCR memakai token scope minimum.
  • [ ] Log rotation Docker aktif (/etc/docker/daemon.json) dan ada pemantauan disk.

Observability minimum

Pemeriksaan otomatis sederhana (systemd timer atau cron harian):

#!/usr/bin/env bash

disk=$(df --output=pcent / | tail -1 | tr -dc '0-9')
[ "$disk" -lt 85 ] || echo "ALERT: disk ${disk}% $(date -Is)" >> ~/alerts.log

Pelajaran 5.6 — Simulasi insiden dan demo

Tujuan

Berlatih diagnosis di bawah tekanan, dengan alur yang jelas.

Alur diagnosis umum

1. Apa yang dilihat pengguna? (kode, pesan, sejak kapan)
2. Lapisan mana?        DNS -> firewall -> port -> proses -> Nginx -> aplikasi -> database
3. Buktikan per lapisan dengan satu perintah, jangan menebak
4. Ubah satu hal, uji lagi, catat hasilnya
5. Setelah pulih: tulis penyebab dan pencegahan

Insiden 1 — 502 Bad Gateway

curl -sI http://127.0.0.1:3000/health        # aplikasi hidup?
docker compose ps                            # container running?
docker compose logs --tail 50 api            # error aplikasi?
sudo tail -50 /var/log/nginx/error.log        # pesan Nginx: connect() failed / upstream

Penyebab umum: container mati, port berubah, aplikasi crash saat start, upstream menunjuk port salah.

Insiden 2 — Container restart loop

docker compose ps                 # Restarting?
docker inspect -f '{{.State.ExitCode}} {{.State.Error}}' $(docker compose ps -q api)
docker compose logs --tail 100 api
docker compose config | grep -A5 environment

Penyebab umum: env wajib kosong, migrasi database gagal, port bentrok, izin volume.

Insiden 3 — Deploy sukses tapi aplikasi tidak berubah

ssh deploy@IP 'cd ~/apps/app && cat .env && docker compose ps'
docker inspect -f '{{.Config.Image}}' $(docker compose ps -q api)
docker compose pull && docker compose up -d --force-recreate

Penyebab umum: tag latest yang di-cache, .env tidak diperbarui, up -d tidak dijalankan setelah pull.

Insiden 4 — Sertifikat kedaluwarsa

echo | openssl s_client -connect app.example.com:443 -servername app.example.com 2>/dev/null | openssl x509 -noout -dates
systemctl list-timers | grep certbot
sudo certbot renew --dry-run
sudo certbot renew --force-renewal && sudo systemctl reload nginx

Penyebab umum: timer mati, port 80 tertutup (validasi HTTP-01 gagal), DNS berubah.

Insiden 5 — Disk penuh

df -h /
du -sh /var/lib/docker /var/log /home/* 2>/dev/null | sort -h
docker system df
journalctl --disk-usage
sudo journalctl --vacuum-time=7d
docker image prune -f          # aman: hanya image tanpa tag

Peringatan: jangan langsung docker system prune -a --volumes; itu bisa menghapus data database.

Verifikasi (demo akhir)

Presentasikan 8 menit:

  1. Arsitektur: repo → Actions → GHCR → VPS → Docker → Nginx → pengguna.
  2. Demo: satu commit → deploy otomatis → situs diperbarui.
  3. Demo: rollback ke versi sebelumnya.
  4. Demo: satu insiden disimulasikan (matikan container atau rusak health check) dan didiagnosis di depan penguji, sambil menyebut perintah dan alasannya.

Cek pemahaman

  3. Bagaimana membuktikan deploy benar-benar menerapkan versi baru? — Bandingkan tag image di .env/docker inspect dengan commit yang di-push, lalu uji /health.
